# 设计笔记

这份文档记录**为什么这么写**，而不是写了什么。代码会过期，判断不会。

---

## 1. 为什么自己写 SSE 客户端

`EventSource` 看起来刚好够用，但有三个硬伤：

1. **只能 GET**。Agent 的输入是一段结构化上下文（历史、工具结果、模型选择），放 query string 既超长又会被日志记下来；
2. **不能带自定义 header**。鉴权、租户、追踪 ID 都要塞进 cookie 或 URL；
3. **重连策略是黑盒**。浏览器自己决定退避和重试次数，你既不能只对 5xx 重试，也不能在 401 时立刻停下。

所以传输层就是 `fetch` + `ReadableStream` + 一个纯函数分帧器。代价是两百行代码和一堆边界（CRLF、多行 `data:`、注释心跳、半个帧跨 chunk），收益是**所有策略都在自己手里**。

---

## 2. 为什么 POST 里要带 `clientTurnId`

断点续传需要服务端知道"这次请求是哪一轮的续传"。

`Last-Event-ID` 只能表达"从哪个游标之后继续"，表达不了"继续哪条流"。真实网关在断连后重放请求时，如果没有业务侧的 turn 标识，服务端会当成一次全新的对话。

做法：传输层每次 `open()` 生成一个 `clientTurnId`，**同一次 open 内的所有重试复用同一个值**（因为 `SseClient` 的 body 在创建时就固定了）。服务端用它做会话键，`Last-Event-ID` 做游标，两者正交。

副作用：服务端要有会话回收（示例里在流结束后 `sessions.delete`），否则内存会涨。

---

## 3. 重试策略：只重试"可能自愈"的错误

```ts
export function shouldRetryStatus(status: number): boolean {
  if (status === 0) return true          // 网络层
  if (status === 408 || status === 429) return true
  return status >= 500
}
```

4xx 里除了 408/429 都不重试：会话不存在、未登录、已被裁决——重连一万次也还是这个结果，只会把"快速失败"拖成"转圈 30 秒"。

退避是 500ms 起步、2 倍增长、上限 7s、最多 8 次。**不采纳服务端下发的 `retry:`**：那个字段描述的是"这个服务端希望的节奏"，而客户端才知道用户当前在不在等、有没有别的请求在竞争。

失败上限是必须的。没有上限的重连在服务端持续 500 时会变成前台静默的 DDoS。

## 4. EOF 不是"结束"，"turn.end" 才是

最初的实现把"流正常关闭"当成回合结束，结果踩了一个坑：**代理在转发 SSE 时可能把上游的异常终止变成一次干净的 EOF**。前端收到 `done`，以为模型说完了，直接把半截回答落库。

现在的语义：

- `turn.end` → 业务意义上的结束，store 主动 `close()` 掉连接；
- 任何 EOF（无论干净与否）→ 都当成"没等到 `turn.end` 的断流"，进入重连。

这意味着**服务端必须显式发 `turn.end`**，不能靠关连接表达结束。这条写进了协议约定。

## 5. 空闲看门狗：为半开连接准备

TCP 半开连接在应用层看起来是"完全正常"的：socket 还在，`read()` 只是永远不返回。三个常见来源：

- NAT/防火墙把空闲连接表项清掉；
- 负载均衡到 idle timeout 直接丢包，不回 RST；
- 反向代理挂住了已经死掉的上游（本项目在演示里就复现了这个：Vite 代理在上游被 `destroy()` 后仍保持浏览器侧连接）。

所以有 `idleTimeoutMs`：超过 N 毫秒没有任何帧（包括心跳），`reader.cancel()` 并走重连。默认关闭，因为不同业务的首帧延迟差异太大——一个需要 40s 冷启动的检索型 Agent，默认 20s 会把它误杀。

**心跳的意义**：如果服务端在长时间思考时会发 `ping`，看门狗就能区分"确实在算"和"连接死了"。

## 6. 增量 Markdown：分块 + 缓存，不碰 innerHTML

三个方案对比：

| 方案 | 每 token 成本 | 安全性 | 结论 |
| --- | --- | --- | --- |
| 全量 `markdown-it` + `innerHTML` | O(全文) parse + 整树 diff | 需要 DOMPurify，且模型输出的是不可信文本 | 长回答掉帧，风险高 |
| 全量 parse 成 React 树 | O(全文) parse | 安全 | 仍然掉帧 |
| **按块切分，只重解析尾块** | O(全文) 扫描 + O(尾块) 解析 | 安全（构造节点，不用 innerHTML） | 采用 |

切块规则：空行结束段落；标题/分割线/围栏代码自成一块；列表按有序/无序分组；**未闭合的块标记 `closed: false`，不进缓存**。

为什么不用 `innerHTML`：模型输出是外部输入。走 HTML 就等于把 XSS 防线交给模型的"心情"，还要额外背一个 sanitizer 的维护成本。构造 React 节点天然转义，链接再做一次协议白名单（`javascript:` / `data:` 直接降级为纯文本）。

**缓存的边界**：缓存键是"块类型 + 语言 + 内容"，命中后直接复用元素树。React 元素是不可变的，复用不会跳过子组件状态。

不支持的语法（表格、内联 HTML、嵌套列表）是**刻意的**：每多一种语法，就多一类"流式中间态"的边界情况（比如表格在列数还没齐的时候怎么渲染）。对话场景里这些结构出现频率低，收益不抵成本。

## 7. 一帧一次渲染

模型每秒能吐 20–60 个 delta。每次 `setState` 都触发一次 React 渲染，等于把时间全花在重复计算上——浏览器一帧最多画一次，多出来的渲染全是浪费。

做法是**状态立即更新、通知按帧合并**：

```ts
const scheduleFlush = () => {
  if (scheduled) return
  scheduled = true
  pending = scheduler.schedule(notify)   // 默认 requestAnimationFrame
}
```

`getSnapshot()` 永远返回最新状态，所以不会读到旧值；订阅者每帧最多被叫醒一次。测试里换成同步调度器，断言就是确定的。

配合 `useSyncExternalStore`，还顺带解决了并发渲染下的**撕裂**问题：流式更新是典型的外部高频源，`useState + useEffect` 很容易读到半新半旧的快照。

## 8. 工具参数：宁可显示原文，也不要猜

模型生成工具参数是逐字符的，`{"query": "杭州` 这种中间态会持续几百毫秒。

`repairPartialJson` 只做**语法层**的收尾：补未闭合的括号、去掉悬空逗号、给悬空冒号补 `null`。一旦截断在字符串中间就放弃，UI 显示原文 + "参数生成中"。

为什么不做更聪明的修复（比如猜一个完整字符串）？因为**用户会当真**。界面上出现一个看起来完整的参数，用户会以为模型就是这么调的；一旦和实际请求不一致，排障成本远高于"多看一眼原文"。

同理，工具卡默认折叠，出错时默认展开——错误信息不应该藏在一次点击后面。

---

## 9. 为什么是 React

这个库的判断大多与框架无关（分帧、续传、折叠、缓存）。选 React 是因为：

- `useSyncExternalStore` 是当前唯一"官方支持外部可变源 + 并发渲染"的原语；
- 工具卡、消息列表这类组合 UI 需要强类型 + 组件边界；
- 目标读者（Agent 产品的前端团队）大概率在 React 生态里。

如果换 Vue，映射关系是：`useSyncExternalStore` → `shallowRef` + `markRaw` + `triggerRef`；`useMemo` 缓存块 → `computed`；组件 `memo` → `defineComponent` + `shouldUpdate`。**状态机本身一行都不用改**——这也是把 reducer 抽成纯函数的原因。

---

## 10. 还没做的事

- **消息虚拟化**：现在整段渲染，几万字以上需要套虚拟列表（难点是单条消息内部不能虚拟，否则选中和复制会坏）。
- **章节级重试**：目前重试是整轮重发。生产上更合理的是"从失败的阶段继续"，这需要服务端支持 `resumeFrom`。
- **多端适配**：窄屏只是退化为单栏，没有做信息架构级别的降级。
- **鉴权刷新**：token 过期发生在流中间时，现在只能整轮重连；更好的做法是带一个 `authorize()` 回调，在 401 时刷新后重放。
